# 统一订单资料读取 interface

Status: ready-for-agent

## Problem Statement

两类业务的资料读取结果结构不同。调用方需要理解分类、命名、必填和证明材料规则，修改容易遗漏一处。

## Solution

订单资料读取 module 返回统一结果。现有文件、处理结果和提示保持一致。

## User Stories

1. 作为用户，我希望家电电脑文件名和同地址去重保持一致，以便继续核对资料。
2. 作为用户，我希望数码全部模板图片及必填规则保持一致，以便保留完整资料。
3. 作为用户，我希望缺失资料仍整笔跳过，以便避免半套下载。
4. 作为用户，我希望证明材料不唯一仍失败，以便避免错误资料。
5. 作为用户，我希望清单原因和材料修改备注保持一致，以便沿用核对流程。
6. 作为用户，我希望登录失效、回滚、续传和并发限制保持一致，以便可靠恢复。
7. 作为维护者，我希望调用方使用同一个 interface，以便集中修改业务规则。

## Implementation Decisions

- 使用已有 assets interface 和请求依赖 seam，不增加 module 或 adapter。
- 两类业务均返回 files、missing、notices。files 是最终文件名到图片地址的映射；missing 是可直接写入清单的缺失原因数组；notices 是需要按原阶段记录的提示数组。
- 数码缺失原因保留“必填图片缺失：”和名称列表；家电电脑保留“SN码或发票图片缺失”。
- 资料读取 implementation 集中命名、去重、必填判断及证明材料唯一性校验。先处理必填缺失，再检查证明材料唯一性，保留现有优先级。
- 调用方仅处理缺失、图片验证、提示及下载。删除旧返回结构和调用分支。
- 不改变持久化格式、账号规则或后台信任检查。

## Testing Decisions

- 用户已同意通过统一 interface 验证命名、缺失原因、证明材料限制和四列清单。
- 使用已有请求 fixture 验证统一 interface，包括必填缺失与证明材料歧义同时存在的优先级。
- 更新已有内容和并发 fixture 的返回合同，不保留旧结构适配。
- 运行完整测试、语法检查及隔离 Chrome 下载流程，核对真实生成图片字节、文件名及清单。

## Out of Scope

新增业务、重构任务存储、修改界面、修改图片下载规则、恢复账号归属校验。
